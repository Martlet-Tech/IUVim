# 24 · 任务书 M7：x86 架构支持（双架构 TSF 文本服务）

> 状态：**已结案**（2026-08-19 决策冻结，未写代码）。
> 触发事件：网易邮箱大师（`mailmaster.exe`，32 位）正文输入完全无输入法（字母直通、无法切换中英），
> 排查日志发现该进程**零记录**（连 Activate 都没有）→ 根因 = 输入法 DLL 仅 x64，无法注入 32 位进程。
> 前置阅读：`00-overview.md`（§4"仅 x64"）、`01-contract.md`、`22-m6-daemon.md`（x86 槽位 §5/§7）、
> `30-conventions.md`。

## 1. 目标（验收一句话）

编译并注册 **x86（i686）版 `iuv_tsf.dll`**，与现有 x64 版**同一 CLSID/TIP 并存注册**：
系统按进程架构自动加载对应 DLL（32 位进程 → x86 DLL、64 位进程 → x64 DLL），**用户完全无感**
（语言栏仍是一个"iuv 输入法"，切换/候选/设置全部一致）。网易邮箱大师等 32 位应用即可正常输入。

## 2. 背景与根因（2026-08-19）

- 现象：在网易邮箱大师邮件正文敲字母直接上屏，Ctrl+Space 切换无效。
- 日志（`%TEMP%\iuv-tsf.log`，清空后重测）：只有 WindowsTerminal（x64）与 explorer 的会话记录，
  **mailmaster.exe 没有任何一行**——TSF 服务在该进程内根本没被激活，不是按键/切换逻辑问题。
- 根因：架构不匹配。`iuv_tsf.dll`（`%ProgramFiles%\iuv\`，PE machine `0x8664` = x64）为 x64 独占；
  网易邮箱大师 `C:\Program Files (x86)\Netease\MailMaster\...\mailmaster.exe` 为 **32 位**（PE `0x014C`）。
  64 位 COM inproc 服务 DLL 无法被 32 位进程加载 → 该进程内输入法整体失效。
- 对照：同机 msedge 为 x64（PE `0x8664`）、WindowsTerminal 为 x64 → 输入法正常，佐证"仅架构问题"。

## 3. 双架构自动解析机制（用户无感的原理）

- 同一 CLSID 在**两处注册表视图**各写一个 `InprocServer32`：
  - `HKCR\CLSID\{GUID}\InprocServer32` → x64 DLL（64 位 `regsvr32` 写入 native 视图）
  - `HKCR\WOW6432Node\CLSID\{GUID}\InprocServer32` → x86 DLL（32 位 `regsvr32` 写入时
    WoW64 重定向自动落此视图）
- 进程激活文本服务时，COM 按**自身进程架构**查对应视图并加载 DLL：
  - 64 位进程查 native 视图 → 加载 `iuv_tsf.dll`（x64）
  - 32 位进程（WoW64）查 Wow6432Node 视图 → 加载 `iuv_tsf_x86.dll`（x86）
- TSF 侧只有**一个** TIP 注册（native + WOW6432Node 两份 `HKLM\SOFTWARE\[WOW6432Node\]Microsoft\CTF\TIP\{GUID}`
  同 CLSID/同 Profile GUID/LangID），语言栏仍显示一个 "iuv 输入法"；架构选择由系统完成，
  对用户与应用**完全透明**。这是搜狗/Rime/QQ 等双架构 IME 的标准做法。
- 唯一"非无感"点：**部署过渡期**——装好后正在运行的 32 位程序需重启一次才会加载新 x86 DLL；
  之后新开的 32/64 位程序全部自动生效。

## 4. 架构与部署布局

```
%ProgramFiles%\iuv\
├── iuv_tsf.dll        x64（现有，不变）
├── iuv_tsf_x86.dll    x86（新增）
└── iuv-daemon.exe     x64（不变，32 位 DLL 同样可拉起，跨架构 CreateProcessW 无碍）

注册表（同一 CLSID {C69735F1-...}，两视图并存）：
├── native 视图：HKCR\CLSID\{GUID}\InprocServer32 → …\iuv_tsf.dll
│                HKLM\SOFTWARE\Microsoft\CTF\TIP\{GUID} + LanguageProfile/Category
└── WOW6432Node 视图：HKCR\WOW6432Node\CLSID\{GUID}\InprocServer32 → …\iuv_tsf_x86.dll
                     HKLM\SOFTWARE\WOW6432Node\Microsoft\CTF\TIP\{GUID} + LanguageProfile/Category
```

### 跨架构互操作可行性（已核实，均安全）

- **共享段**（`iuv-data/src/shm.rs`）：固定 20 字节头（`IUVSHM01` magic + 三个 u32 字段）+ 变长字节
  数据区，**无指针/usize 跨进程布局** → 32 位 DLL（ShmReader）↔ 64 位 daemon（ShmWriter）直接共享。
  `AtomicU32::from_ptr` 在 x86/x64 上对对齐 u32 均原生原子。
- **命名管道**（`iuv-data/src/ipc.rs`）：静态名 `\\.\pipe\iuv-userdict` + 自定义字节编码
  （`encode_request/Response`）→ 架构中立。
- **daemon 自启**（`iuv-tsf/src/daemon_client.rs` `daemon_exe_path`）：经 `registration::dll_path()`
  （`GetModuleHandleExW` 反查 DLL 自身）解析同目录 `iuv-daemon.exe`——x86 DLL 同理解析成功；
  CreateProcessW 从 32 位进程拉起 64 位 exe 无碍。
- **候选窗/设置页**：iuv-ui（tiny-skia + cosmic-text）纯 Rust 支持 i686；daemon 设置页与架构无关。

## 6. 已知风险与取舍

- **双架构同 CLSID 是标准做法**但需手测确认：语言栏不出现重复"iuv 输入法"条目；两个 `regsvr32`
  注册顺序任意（native 与 WOW6432Node 视图互不覆盖）。
- i686 构建工具链缺失（rustup target / 32 位 MSVC linker）需先安装，属一次性前置。
- iuv-ui 依赖（tiny-skia/cosmic-text/swash）在 i686 编译如遇架构相关 SIMD 代码，需确认 feature 默认
  关闭或降级纯标量（风险低，均为纯 Rust）。
- 老 x64 进程不受影响（仍持旧 x64 DLL）；**32 位进程需重启一次**才能加载新 x86 DLL。
- 卸载必须同时清 WOW6432Node 键，否则残留视图会导致 32 位进程仍尝试加载已删 DLL。
- 守护进程保持 x64：无需双架构 daemon（架构中立 IPC/SHM 已核实）；x86 会话进程降级逻辑不变。
