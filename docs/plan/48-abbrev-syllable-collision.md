## 1. 背景与现象（repl 实测复现）

敲 `fa`，1 号候选是**方案**（Word 27240），压过 发（Char 22519）/法；敲 `la`，
**恋爱**（6795）排 3 号插进 啦/拉 与 辣 之间，另有利安/立案/里昂/两岸等一堆混入。
微软拼音与小狼毫均无此行为（`fa` 首屏只有单字）。

候选分数列（`-9.6699` = `ln(weight) − ln(total)`）显示这批词**零可信度罚分**，
与全拼单字同池按原始词频直排。

## 2. 归因：M1.5 简拼键预生成与完整音节撞键

1. dictc 为 ≥2 音节词预生成简拼键（`compile.rs::abbrev_of`：每音节首字母串联，
   权重原样复制，与全拼键同表混存）：`fang'an`(方案)→`fa`、`lian'ai`(恋爱)→`la`。
2. 键空间隔离的设计前提（01-contract §3 注释）："简拼键不含 `'` **且非完整音节**，
   只在多段简拼输入时被查询"——但 `fa`/`la`/`ha`/`ka`/`ma`/… 这类词的简拼串
   **本身就是合法音节**，前提不成立且无人守卫。
3. 查询路由（§4.2）把整串 `fa` 判为"完整单音节"→ 走 `dict.exact("fa")` 纯单字档，
   该查询直接命中同表混存的简拼键副本 → 方案以满权重进池并赢过 发。
   判别实验：`la` 桶里 恋爱/立案/两岸 等全部命中（简拼 l+a 形态词一网打尽）。
4. 小狼毫对照：librime 不预存简拼键，拼写图动态派生简拼边并逐边累加
   credibility `ln(0.05)`（两简拼音节 ≈ ×0.0025），天然沉底；微软更严，首屏不给。

## 3. 方案 A（用户裁决采纳）：编译期过滤

`abbrev_of` 产出的简拼串若 `format::is_syllable` 为真 → 返回 `None`（不生成该键）。

- 音节表零新增依赖：`iuv-data/src/format.rs` 已有 `SYLLABLES` 常量表 +
  `is_syllable()`（本仓唯一音节真相源，写端建元数据音节段同源使用）。
- 行为代价：敲 `fa`（或显式 `f'a`）再也到不了 方案——**这正是微软行为**，
  符合 M1.5"对齐微软"政策；`fangan` 全拼照常。真正的简拼主力键族（`nh`/`tam`
  等非音节形）不受影响。
- 波及面：仅词库产物变化（条目略减），引擎代码与二进制格式不动；
  所有加载旧 imedic 的实例行为不变，重编译即生效。

**否决的替代**：B. 简拼键加 `'` 分隔隔离键形（改动面大：编译器+查询键族+契约三处）；
C. 查询侧对 exact 结果按词长猜罚分（存储层无法区分两族，语义 hack）。
