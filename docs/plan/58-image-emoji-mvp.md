# 58 · 图片表情 MVP（剪贴板粘贴通道 + 注入键识别）

> 状态：**通道实测通过，MVP 待决策**（2026-10-18）。优先级**低于 59 号英文补全**——
> 本文的价值是固化实测结论与实现方案，避免"要不要做表情包"被反复重推。
> 前置阅读：`16-command-mode.md`（i/u/v 命令体系）、`54-pet-mount.md`（ULW 面板先例）。

## 1. 实测结论（2026-10-18，真机，搜狗 16.7.0.4912 + 微信 PC）

三轮实测，结论逐条修正：

| # | 原判断 | 实测结论 |
|---|---|---|
| 1 | "打字出表情候选"是主流交互 | **错**。PC 端只有面板点击，候选栏联想在 16.x 已弱化，且只认"我的收藏" |
| 2 | 图上的红字可被文字联想命中 | **错**。红字是像素，逐图 tag 缺失；只有包级 tag（"暴走"） |
| 3 | PC 无法把图片送进光标处 | **半错**。TSF 无图片 API（正确），但**剪贴板 + 模拟 Ctrl+V 这条路是通的** |
| 4 | 面板点图 = 3 步操作 | **错**。搜狗点图 = 写剪贴板 + **自动粘贴**，1 步完成 |

**关键证据**：在微信输入框点搜狗面板一张图 → 出现一张；紧接着手动 Ctrl+V → **又出现一张同样的**。
证明搜狗的实现是「写剪贴板 → SendInput Ctrl+V」，且**粘贴后不恢复剪贴板**——用户原有剪贴板内容被永久替换。

**副作用**：这正是用户感知到的"污染"。搜狗不处理，是 iuvim 的差异化切口（见 §3.5）。

## 2. 方案定位

不做"候选栏出图"（会污染打字候选，且与文本候选语义冲突），只做**收藏面板**：

```
热键 / 工具栏按钮 → 自绘收藏面板（ULW，NOACTIVATE）→ 点图 → 写剪贴板 → 自动 Ctrl+V → 恢复剪贴板
```

**1 步操作 + 剪贴板不脏**，严格优于搜狗。

## 3. 实现拆解

### 3.1 面板 UI（复用现有底盘）

- 宿主窗口：`WS_EX_NOACTIVATE | TOPMOST | TOOLWINDOW | LAYERED`，`WM_MOUSEACTIVATE → MA_NOACTIVATE`
  （与 `badge.rs` / `candwin.rs` 同款，已具备）
- **形态：transient 面板，不做独立窗口**（2026-10-18 决策，见 §3.1.1）——
  无标题栏、无最小化/关闭按钮、不进任务栏、点击外部或选完即隐藏
- 渲染：`iuv_ui` 复用 toolbar 的 tiny-skia 路径 + 缩略图解码（新增 `image` crate 需白名单审批）
- 布局：网格 4×N，最近使用置顶

#### 3.1.1 反面教材：搜狗的表情面板是"独立工具窗口"

实测截图显示该面板带**标准标题栏（最小化 `_` / 关闭 `×`）**、文件管理器式工具条
（导入表情 / 删除表情）、底部分类 tab。这套 chrome 说明它是"附带的桌面小工具"，
**不是输入法能力的一部分**——这也解释了为什么它跟打字链路零耦合（打字不出表情候选）。

推论（用户直觉验证）：`_` 的存在暗示"可以常驻"，但 600×500 的常驻面板会遮挡内容，
真实使用必然是"用完就关"，而不是"一直开着想点就点"。**"挡了就最小化"不是功能，
是形态错误的症状。**

iuvim 若做，必须反过来：面板 = 候选窗的兄弟（ULW、无边框、瞬态、跟随工具栏/光标），
而不是一个需要用户管理的窗口。这是形态层面的差异化，成本几乎为零。

**入口成本实测（2026-10-18）**：搜狗发一张图的完整路径 =
悬停工具栏键盘 logo → 点开工具箱 → 点「图片表情」→ 面板出现 → 点图
= **4 步 + 1 次悬停**。工具箱本身是反模式：语音输入/手写/软键盘/跨屏输入/图片表情/
符号大全/生僻字/添加词库 八项平铺，无主次——这是"功能清单驱动"的产品，不是"场景驱动"。

**决策：表情面板必须一级入口**（专用热键 / 工具栏一级图标单击直达），
**禁止**做"工具箱式二级菜单"。评价标准 = 从"想发"到"面板出现"**1 次操作**。


### 3.2 数据

```
%LOCALAPPDATA%\iuv\stickers\
  index.json          # [{file, added_at, used_count}]
  *.png / *.gif
```

- 用户手动放图 / 从面板"导入文件"，不做云端表情商店（不碰内容审核）
- `used_count` 排序 = "最近使用"，这是表情包玩家的真实高频路径

### 3.3 粘贴链（核心，五步）

```
1. 备份剪贴板（文本 / CF_DIB / CF_HDROP 三种格式，尽力而为）
2. 写 CF_DIB（静态图）或 CF_HDROP（GIF，落临时文件）
3. SendInput(Ctrl+V)
4. 延迟 400ms（等目标应用读完）
5. 恢复剪贴板（条件见 §3.5）
```

### 3.4 注入键识别（iuvim 特有难题，必须做）

**问题**：`SendInput` 发出的 Ctrl+V 会先进 iuvim 自己的 `OnTestKeyDown`。
不处理 → 递归或把 Ctrl+V 当打字送进会话。

**方案（二选一，建议 A）**：

- **A. 全局注入标记**：发键前置 `INJECTING: AtomicBool`，`key_routing.rs` 最前部检查并直接放行 + 清标记。
  缺点：有理论竞态窗口（用户恰在此刻真按 Ctrl+V）。
- **B. 低级键盘钩子**：`WH_KEYBOARD_LL` 看 `KBDLLHOOKSTRUCT.flags & LLKHF_INJECTED`。
  准确但要常驻钩子（安全软件敏感度高）。

**建议 A**，并在标记里带时间戳（500ms 内有效），把竞态窗口压到可接受。

### 3.5 剪贴板恢复的竞态（差异化关键）

恢复早了目标还没读完，恢复晚了覆盖用户新复制的内容。解法：

```
before = GetClipboardSequenceNumber()   // 写完剪贴板后取
... 400ms ...
if GetClipboardSequenceNumber() == before { 恢复备份 } else { 放弃恢复 }
```

序号变了 = 期间有别人（含用户）动过剪贴板 → 不恢复，避免二次污染。
**这一条搜狗没做，是我们能明确宣称的优势。**

## 4. 已知限制（必须在 UI 上诚实标注）

| 限制 | 说明 |
|---|---|
| 仅接受图片粘贴的宿主 | 微信 / QQ / 记事本 / Word 预期可；Electron 一半；游戏/管理员程序基本不可 |
| UIPI | iuv-server 普通权限，管理员进程接不住 SendInput（静默失败） |
| GIF | 必须 CF_HDROP + 临时文件，微信会当文件发送（形态不同于静图） |
| 安全软件 | SendInput + 剪贴板 = 键盘记录器特征，可能被拦 |

面板底部固定一行提示：**"仅在支持图片粘贴的应用中可用"**，不做通用能力宣传。

## 5. 不做

- 候选栏出图（污染打字）
- 云端表情商店 / 内容审核
- 表情包"关键词联想"（逐图 tag 缺失，数据源不存在）
- 剪贴板历史管理（超出输入法职责）

## 7. 优先级与风险

- **优先级**：低于 59 号。理由：一是"偶尔发图"，二是用户本人不用表情包（无 dogfooding）。
- **最大风险**：做出来"时灵时不灵"。建议实施前先手动发 20 张图统计失败率，>15% 就不做。
- **成本估计**：面板 UI + 粘贴链 + 注入识别 ≈ 500~700 行（含测试），新增 1~2 个白名单依赖。

## 8. 设计 B：词条化表情输入（2026-10-18 用户设计，**推荐替代 §2/§3 的纯面板方案**）

> 设计 B 与 §2 的本质差别：表情不是"外挂面板"，而是**候选管线的一部分**。
> 这正好补上搜狗架构上缺失的那一环（§3.1.1）——它不是窗口，是候选。

### 8.1 核心：表情挂在词条上

- **词条 = 语义分组**：`开心`（code `kai xin`）下挂 N 张图（猪/狗/猫的开心图）
- 检索靠**用户自己建的词条名**，不依赖逐图 tag（§1 已证伪的路径）
- **建表情词条时自动写入用户词库**（56 号 `UserMutation`），避免"图库有 code、词库没词条"
  的双真相源；删词条 → 图进孤儿区待清理
- 存储：`%LOCALAPPDATA%\iuv\stickers\index.json` + `<code>/001.png`

### 8.2 两级候选

```
第一级：普通候选行，带图词条加角标（复用 Candidate 的 cm 备注位，不新开字段）
第二级：图片列表，展开在候选窗下方/右侧，导航上下文整体切换
```

### 8.3 手势（全部复用现有语义，零新概念）

| 层 | 空格 | 数字 1-9 | Tab | Shift+←/→ | Esc | Backspace |
|---|---|---|---|---|---|---|
| **候选层** | 上屏文本 | 上屏第 n 个 | **下钻**（仅高亮项带图） | 调权（现状） | 取消会话 | 删字 |
| **图片层** | 上屏图 | 上屏第 n 张 | — | **调图序** | 回候选层 | 回候选层 |

- **Tab 只在"高亮项带图"时拦截**，其余情况放行给应用（写代码的 Tab 缩进不受影响）
- **Shift+←/→ 在图片层复用为"调图序"**——与候选层调权同一心智模型，用户零学习成本。
  这是设计 B 最优雅的一处：M2 的核心卖点（用户掌控排序）自然延伸到表情。
- **不做 Shift+数字**（原因见 §8.5）

### 8.4 架构接口

| 层 | 改动 |
|---|---|
| `SessionAction` | 新增 `ExpandImages` / `ImagePrev` / `ImageNext` / `ImageCommit` |
| `config/keymap.rs` | 零结构改动（已是 `Combo` 可配），只加默认绑定 |
| `iuv-proto` | **加一个字段**：`UiSnapshot.highlight_has_image: bool`（PROTO 4→5） |
| `iuv-tsf` | `OnTestKeyDown` 按该字段决定 Tab 拦/放（唯一改动点） |
| `iuv-core` | 会话状态机加"图片层"子状态；图片候选独立列表 |
| `iuv-ui` | 新增图片网格布局 + 缩略图缓存 |

**上屏时序（关键）**：先结束会话（清 composition）→ 再写剪贴板 + `SendInput Ctrl+V`。
顺序反了会把预编辑文本一起提交或留残影。

### 8.5 键位打架点（2026-10-18 记录，供设计者再想）

逐手势对现状核对（`crates/iuv-core/src/config/keymap.rs` 已核实）：

| 手势 | 层 | 现状占用 | 冲突性质 | 结论 |
|---|---|---|---|---|
| `←` / `→` | 候选层 | `CandidatePrev` / `CandidateNext`（keymap.rs:173-174） | 无 | 直接复用 |
| `←`/`→` + 空格 | 候选层 | 空格 = 上屏首候选 | 无 | 复用 |
| 数字 `1-9` | 候选层 | 数字 = 上屏第 n 个 | **语义风险**：带图词条误上屏文本，TSF 无 undo | 待定（§8.7-1） |
| `←`/`→` + `Tab` | 候选→图片 | **`Tab` 完全未映射**（29 号已核实） | 见 §8.6-1 三方争夺 | 可行，需仲裁 |
| `Shift` + 数字 | 候选→图片 | `Shift+1`=`!`、`Shift+2`=`@`…走符号上屏 | **物理键冲突，不可行** | 砍掉 |
| 空格 | 图片层 | 候选层 = 上屏文本 | 上下文隔离即可 | 可行 |
| 数字 `1-9` | 图片层 | 候选层 = 上屏第 n 个 | 上下文隔离即可 | 可行 |
| `Shift`+`←`/`→` | 图片层 | 候选层 = `SwapLeft`/`SwapRight`（调权） | 需作用域切换（调权对象从候选变图） | 可行，**最优雅的复用** |
| `Esc` | 图片层 | 候选层 = 取消会话 | 需新增"层级回退"语义 | 必须新增 |
| `Backspace` | 图片层 | 候选层 = 删字 | 需上下文隔离 | 必须新增 |
| 翻页键 | 图片层 | 候选层翻页 | 上下文隔离 | 复用 |
| **一步直达图列表** | — | 无 | Alt 组合不进 TSF（死路）；Ctrl+数字被应用占用；Shift+数字物理冲突 | **没有干净的键位**，只能接受两步 |

### 8.6 三个真正没解决的争夺

**1. `Tab` 是四方争夺**

| 主张方 | 用途 |
|---|---|
| `29-tab-ideas.md` A | 把高亮移到"翻译槽"（N+1 号位） |
| `29-tab-ideas.md` B | 钉选当前候选续打（不结束会话） |
| 本文 58 号 | 对带图词条下钻图列表 |
| 宿主应用 | 缩进（写代码/填表） |

四者语义不同但都指向"下一个层级/下一个东西"。**必须先定 `Tab` 的唯一语义**，否则三份任务书会互相打架。
可行方向：上下文分流（有图词条高亮 → 下钻；翻译槽可见 → 跳槽；否则放行给应用），
但"分流规则本身"就是复杂度，需要设计者拍板。

**2. `Shift`+数字：不可行**

`Shift+1` 物理上就是 `!`。要劫持得在符号映射之前特判，且用户在符号/英文输入时会被误伤。
收益（省一次 `Tab`）远小于风险，建议永久放弃。

**3. "一步直达"没有干净键位**

结论：**表情列表只能两步进入**（定位词条 → `Tab`）。这是键盘输入法的固有限制，
不是设计缺陷——手机端能一步是因为有触摸。

**已定的规避（无需拍板）**

- **单图词条**：只有 1 张图时不展开，`Tab` 直接上屏那张。
- **图片解码延迟**：候选阶段后台预解码当前页缩略图，展开时零等待。
- **Alt 组合**：不用（`WM_SYSKEYDOWN` 不进 TSF 键 sink，机制死路，见 AGENTS.md）。
- **数字键两层语义**：靠上下文隔离（图片层不显示文本候选），用户不会混。

### 8.7 待定（需拍板）

1. **带图词条的数字键行为**：上屏词条文本（原设计）vs 下钻图列表。
   风险点：前者在带图词条上是高概率误操作，且 TSF 上屏无 undo。
2. **纯图词条的空格行为**：上屏词条名 vs 直接展开图列表。
3. **图片层布局**：横排 1×N（与候选窗同高，改动小）vs 网格 2×5（一次看 10 张，好用）。
