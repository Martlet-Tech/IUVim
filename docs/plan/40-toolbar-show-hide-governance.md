# 工具条显隐状态治理（探索历程 + 最终定稿）

> 状态：**已定稿落地**（`minimal-signal` 分支 → main，2026-08-22）。
> 本文保留完整探索历程——三维信号模型是通往小狼毫(weasel) API 调研的关键一步，

## 实验环境与方法

- **计算器选型原因**：推测计算器没有通过 TSF 向输入法转发按键——比 2077 的处理干净；
  或者计算器收到按键后直接丢弃非数字/运算符的部分。即计算器是「零干扰背景」，
  切换焦点的显隐行为不受应用自身按键策略污染。
- **时钟动画帧检测法**：搜狗皮肤带模拟时钟表盘（表针约 2 秒转一圈，动画约 12 帧）。
  记下表针位置 → 快速切换 → 快速切回 → 对比表针偏移：
  - 偏移 1-2 帧 = 隐藏期间窗口存活、动画状态未销毁 →【隐藏】
  - 从头开始/偏移巨大 = 窗口销毁重建 →【关闭】


# 用户结论
1. 维度①：输入法切换至/切出 —— QQ/搜狗之间来回切时，不同皮肤复杂度带来工具条启动时间差异 → 证明存在 TIP 级切换信号，工具条随其开/关（启动耗时 = 皮肤复杂度渲染成本）
2. 维度②：应用切换至/切出 —— 切出时一定发了隐藏信号，才使 QQ/搜狗在两个记事本之间切换时呈现闪烁（隐藏→重显）→ 证明存在即时的焦点切出隐藏信号
3. 维度③：新切入的应用是否支持 TSF —— 结合②：离开焦点执行一次隐藏；若新应用不支持 TSF → 不重显 → 工具条保持隐藏

## 对照实验一：记事本 ↔ 计算器焦点切换（时钟帧检测法）

快速在两个程序间来回切换焦点，多轮。

| 维度 | 搜狗（参照） | iuv（现状） |
|---|---|---|
| 切走瞬间 | 工具栏**消失** | **仍在屏上** ✗ |
| 反复来回切换 | 每次「消失↔重现」 | 恒显，从未隐藏 ✗ |
| 切回后时钟状态 | 表针仅多走 1-2 帧 → **隐藏而非关闭**，窗口存活、状态保留 | —（恒显，无从验证） |
| 定性 | **隐藏 / 恢复** | **从不隐藏** |

**结论**：搜狗对程序切换的处理是「隐藏窗口、保留存活」——这是瞬时恢复体验的前提；
iuv 在同样场景下完全没有隐藏动作。

## iuv 独立观察（无搜狗对照项）

### 观察③ 双记事本四态独立 ✓

记事本 a、b 同时开；a 切英文、b 保持中文。来回切焦点：a 恒英文、b 恒中文。
两个 TSF DLL 实例各存自己的四态变量，互不串扰——符合预期。

### 观察④ 切走输入法再切回，四态丢失 ✗

焦点保持 a，先切到 QQ 输入法再切回 iuv：中英文指示变回中文（英文态丢失）。 
这是正常现象啊， 设置界面的4态语义， 就是初始值，  
所以切到别的输入法再切回来， 肯定换了实例了， 用初始值没任何问题

### 事故⑤ 拖动搜狗工具条时 iuv-daemon 崩溃（挂起）

iuv 与搜狗工具条并存时拖动搜狗的工具条，iuv-daemon 崩溃。日志无 `[panic]` 行、
无退出码行——非 Rust panic，硬崩或外部强杀，根因未定位。

## 参照行为补充：搜狗 / QQ 的细节

- **搜狗 ↔ QQ 反复互切**：离开方工具条瞬间消失（与 Win10 输入法列表消隐可能同帧）；
  新激活方有渲染延迟（搜狗特意带动态工具栏效果，比 QQ 更慢）。
- **含义**：存在一个即时的停用信号，头部输入法在该信号回调内直接隐藏自己的工具条
  （窗口归自己进程，同步隐藏零延迟）。
- **暗黑4 正例**：回车开聊天框 → Activate + 键转发开始；关聊天框 → Deactivate +
  键转发停止。非对话态完全不向 TSF 转发按键（应用责任模型）。

## 当前实现的已知缺口（初步梳理，非定稿）

1. 显隐判定含 `or_else` 兜底分支——僵尸 active 实例（进程被杀未 Deactivate 等）
   会借兜底撑起过头显示【对照实验一 iuv 侧】。
2. 无进程存活检测：异常退出的应用留下的实例条目无法自愈。
3. 实例四态在 IME 切换往返中丢失【观察④】。
4. 自绘窗从不隐藏：无任何路径触发浮动工具条的隐藏动作【对照实验一】。
5. daemon 崩溃根因未知【事故⑤】，暂挂。

# 定稿：双管道分离 + 纯信号三消息协议（2026-08-22）

## 从三维模型到最终架构

因果链：三维模型确立后，为寻找**维度①**的官方信号研究小狼毫(weasel)源码，
发现 `ITfThreadFocusSink` 等一批从未用过的 TSF API → **维度②③**（应用切出/切入）
以官方 sink 落地；**维度①**（输入法切至/切出）探测 sink
（`ITfActiveLanguageProfileNotifySink` 经 `ITfSource` 挂载）实测
`CONNECT_E_CANNOTCONNECT (0x80040202)`，从未产出信号——而既有 OPENCLOSE
compartment 通道本就覆盖了该场景，故休眠摘除。

## 迭代失败记录（简单方案是试出来的）

| # | 尝试 | 失败方式 | log 实锤 |
|---|---|---|---|
| 1 | 消息到达即查 `GetForegroundWindow` 一次性判定 | TSF 焦点通知常跑在系统更新前台窗口之前，显示被静默吞掉 | 连续切换 seq125/128/129 连丢，第 N 次"切回去才重现"，次数随机 |
| 2 | FIFO 化接收端 | daemon 侧零丢失，但发送端仍丢：`set_active` 与用户库写共用忙时即弃管道，单线程 serve + 1500ms WaitNamedPipeW 超时即弃 | 三组对账：TSF 发了、daemon 永远没收到 |
| 3 | profiles 探测 sink | msctf 不接受该挂载路径，维度①信号缺失 | 全部进程一致 0x80040202 |

结论：**独立通道 + 接收端 FIFO 就是充分且必要的全部**——通道不干别的所以永不 busy，
FIFO 保证毫秒级风暴下不丢。无定时器、无前台查询、无任何兜底
（管理员裁决：「好使就是好使，不好使就是没改对地方」）。

## 最终形态

```
TSF 实例 ──激活(+四态)/失焦/态变更──▶ iuv-toolbar-signal 专用管道
                                       │ thread-per-connection 长连接
                                       ▼
                             ToolbarHost::handle_signal → 单 FIFO
                                       │
                   工具条线程 drain：绑定→显示 / 解绑→隐藏 / 换态重绘
数据面（iuv-userdict 字典写）与 CTL 反向通道：物理隔离，互不相干
```

协议（`ToolbarSignal`，tag 0x21-0x23）：

| 时机 | 消息 | 内容 | daemon 动作 |
|---|---|---|---|
| 获得焦点 / TIP 激活 | **激活** | pid+tid+四态 | 绑定该实例 → 显示（渲染其四态）|
| 失去焦点 / IME 切走 | **失焦** | pid+tid | 绑定者本人 → 解绑并隐藏 |
| 会话中途四态变化 | **态变更** | pid+tid+新四态 | 重绘换内容 |

时序颠倒自收敛：Set/Kill 谁先到终态都正确（[B真,A假] 与 [A假,B真] 等价）。
pid/tid 仅作日志观察点（管理员裁决：「重点是『有一个』」）。

## 关键裁决记录

- **不做兜底**：僵尸清扫、断线补发、恢复机制一律不建——daemon 重启后任意焦点事件自然重建一切。
- **UWP 宿主忽视**：ApplicationFrameHost 框架线程若真获得焦点会照常显示，语义自洽。
- **四态持久化不需要**【观察④】：设置页四态即初始值，IME 往返 = 新实例用初始值，符合直觉。
- **隐藏而非关闭**✓：SW_HIDE 窗口存活，重显瞬时（对照实验一的搜狗行为）。
- **崩溃⑤**：后续多轮高强度切换测试未复现，继续挂起观察。

## 实测数据（minimal-signal 分支）

- 激活/失焦成对到达间隔 **0~15ms**；快速互切/记事本↔计算器/注销重登全新时间线
  四轮验证：零丢失、零 panic、零卡状态。
- 时序颠倒样本：`激活(5136)@6453.415 → 失焦(18212)@6453.416` 正确收敛为绑定 5136。
- 热部署间隙的信号扑空（daemon 重启窗口）由「弃缓存下次重连」自然吸收，无需任何补偿机制。
