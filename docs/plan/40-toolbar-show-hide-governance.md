## 实验环境与方法

- **计算器选型原因**：推测计算器没有通过 TSF 向输入法转发按键——比 2077 的处理干净；
  或者计算器收到按键后直接丢弃非数字/运算符的部分。即计算器是「零干扰背景」，
  切换焦点的显隐行为不受应用自身按键策略污染。
- **时钟动画帧检测法**：搜狗皮肤带模拟时钟表盘（表针约 2 秒转一圈，动画约 12 帧）。
  记下表针位置 → 快速切换 → 快速切回 → 对比表针偏移：
  - 偏移 1-2 帧 = 隐藏期间窗口存活、动画状态未销毁 →【隐藏】
  - 从头开始/偏移巨大 = 窗口销毁重建 →【关闭】


# 用户结论
1. 维度①：输入法切换至/切出 —— QQ/搜狗之间来回切时，不同皮肤复杂度带来工具条启动时间差异 → 证明存在 TIP 级切换信号，工具条随其开/关（启动耗时 = 皮肤复杂度渲染成本）
2. 维度②：应用切换至/切出 —— 切出时一定发了隐藏信号，才使 QQ/搜狗在两个记事本之间切换时呈现闪烁（隐藏→重显）→ 证明存在即时的焦点切出隐藏信号
3. 维度③：新切入的应用是否支持 TSF —— 结合②：离开焦点执行一次隐藏；若新应用不支持 TSF → 不重显 → 工具条保持隐藏

## 对照实验一：记事本 ↔ 计算器焦点切换（时钟帧检测法）

快速在两个程序间来回切换焦点，多轮。

| 维度 | 搜狗（参照） | iuv（现状） |
|---|---|---|
| 切走瞬间 | 工具栏**消失** | **仍在屏上** ✗ |
| 反复来回切换 | 每次「消失↔重现」 | 恒显，从未隐藏 ✗ |
| 切回后时钟状态 | 表针仅多走 1-2 帧 → **隐藏而非关闭**，窗口存活、状态保留 | —（恒显，无从验证） |
| 定性 | **隐藏 / 恢复** | **从不隐藏** |

**结论**：搜狗对程序切换的处理是「隐藏窗口、保留存活」——这是瞬时恢复体验的前提；
iuv 在同样场景下完全没有隐藏动作。

## 对照实验二：计算器聚焦时 Win+Space 切换输入法

前置：焦点在计算器，当前输入法 = A；Win+Space 切到输入法 B。此实验为系统级
语义探测（iuv 未参与对照）。

| 观察点 | 结果 |
|---|---|
| 托盘图标（切换瞬间） | **不变**（仍显示 A） |
| 点击桌面使计算器失焦的瞬间 | A 的工具条**立即消失** |
| B 的工具条 | 小延迟后出现（推测为 B 准备渲染内容） |

**结论**：输入法选择是 **per-thread / 随焦点记忆** 的；焦点切换触发
「旧 TIP 停用 → 新 TIP 激活」的即时事件链，工具条显隐跟随这条链而非全局状态。

## iuv 独立观察（无搜狗对照项）

### 观察③ 双记事本四态独立 ✓

记事本 a、b 同时开；a 切英文、b 保持中文。来回切焦点：a 恒英文、b 恒中文。
两个 TSF DLL 实例各存自己的四态变量，互不串扰——符合预期。

### 观察④ 切走输入法再切回，四态丢失 ✗

焦点保持 a，先切到 QQ 输入法再切回 iuv：中英文指示变回中文（英文态丢失）。 
这是正常现象啊， 设置界面的4态语义， 就是初始值，  
所以切到别的输入法再切回来， 肯定换了实例了， 用初始值没任何问题

### 事故⑤ 拖动搜狗工具条时 iuv-daemon 崩溃（挂起）

iuv 与搜狗工具条并存时拖动搜狗的工具条，iuv-daemon 崩溃。日志无 `[panic]` 行、
无退出码行——非 Rust panic，硬崩或外部强杀，根因未定位。

## 参照行为补充：搜狗 / QQ 的细节

- **搜狗 ↔ QQ 反复互切**：离开方工具条瞬间消失（与 Win10 输入法列表消隐可能同帧）；
  新激活方有渲染延迟（搜狗特意带动态工具栏效果，比 QQ 更慢）。
- **含义**：存在一个即时的停用信号，头部输入法在该信号回调内直接隐藏自己的工具条
  （窗口归自己进程，同步隐藏零延迟）。
- **暗黑4 正例**：回车开聊天框 → Activate + 键转发开始；关聊天框 → Deactivate +
  键转发停止。非对话态完全不向 TSF 转发按键（应用责任模型）。

## 当前实现的已知缺口（初步梳理，非定稿）

1. 显隐判定含 `or_else` 兜底分支——僵尸 active 实例（进程被杀未 Deactivate 等）
   会借兜底撑起过头显示【对照实验一 iuv 侧】。
2. 无进程存活检测：异常退出的应用留下的实例条目无法自愈。
3. 实例四态在 IME 切换往返中丢失【观察④】。
4. 自绘窗从不隐藏：无任何路径触发浮动工具条的隐藏动作【对照实验一】。
5. daemon 崩溃根因未知【事故⑤】，暂挂。
