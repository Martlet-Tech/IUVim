# 39 · 引擎 Rime 化改造（分节器/翻译器/过滤器隔离 + 统一打分 + 分段确认交互）

> 状态：方案定稿（2026-08-26），待实施。
> 决策记录：本文档同时充当决策台账——所有方向性取舍（键位、许可、双引擎去留等）
> 均由管理员拍板后记录在案，后续实施不得悄悄推翻。

## 1. 背景与动机

当前 iuv-core 的候选生成是「一个路由器 + 五个各自为政的策略函数」：输入先经
`Engine::classify` 判定档位（Route 枚举），再按档位分派到 routes.rs 的五个手写生成器，
排序靠插入顺序而非分数。这套机制能工作，但积累了结构性问题：

1. **classify 是特判堆积**：档位判定语义等于「枚举微软实测过的所有输入形态」，
   每遇新场景就叠补丁（如 `tail_completable` 就是为救 `shigechengy` 场景追加的判断）。
2. **撇号所有权污染**：会话选词续接时把引擎注入的撇号混进用户原始输入串，导致下游
   无法区分「用户敲的 `'`」和「引擎拼的 `'`」，词条通道里出现靠循环下标的特例
   （routes.rs 的 k==1 破例）来猜测语义。
3. **seg_len 一词三义**：同一个字段在不同候选上分别表示「组句段数 / 词条发现层级 /
   兜底总段数」，消费端需要防御性钳制（曾有越界 panic 被 guard 吞掉）。
4. **分数不传递**：Viterbi 算出的整句路径分只在内部用完即丢，从不上浮到候选；
   「整句 > 匹配长度 > 词频」的三级排序没有统一比较器，散落在各生成器的插入次序里。
5. **过滤逻辑无独立阶段**：屏蔽、去重、截断、兜底分散在查询层、路由函数、引擎尾部
   三处；契约当初规划的 rerank 管线从未落地。

Rime（librime）在这些方面有成熟二十年的答案：分节器（Segmentor）逐段推进打标签、
翻译器（Translator）按标签供候选、过滤器（Filter）链式收尾、Poet 统一组句打分。
本改造把 iuv-core 重塑为同样的形状。

### 对 librime 的调研结论（2026-08 实测源码）

- Rime 的句子产生机制就是词格动态规划（poet.cc 自嘲 "simplistic sentence-making"）：
  无语法组件时走纯 DP（与现有 viterbi.rs 同族）；有语法组件时走束搜索（每个位置按
  「末词」保留前 7 条线）。权重累加公式 = 前缀累计 + Grammar::Evaluate(上下文, 词,
  词条权重)，上下文回看两个词，并携带已确认前文（preceding_text）。
- 平局决胜规则：等权重时偏好词数少的路径（即偏好长词），再比词长序列的字典序
  （左结合）。这正是「长度惩罚」思想的现成实现，可直接采纳。
- Poet 故意排除「单个词覆盖整段」的边——那种候选由词条翻译器负责，句子只做
  多词组合，两通道天然不重复。
- 多句候选接口（MakeSentences）带截止阈值衰减公式，M3 学习候选可直接借鉴。
- **不存在成熟的 librime 纯 Rust 移植**。现存的 librime-rs / librime-api 都是 FFI
  绑定（链接 C++ 库，拖 boost/leveldb/marisa 依赖链）。走 FFI 会破坏依赖白名单制和
  iuv-core 跨平台纯 Rust 定位，已排除。移植只能自己从 C++ 源码改编。

## 2. 目标与非目标

### 目标

- 分节器 / 翻译器 / 过滤器职责清晰隔离，形状对齐 rime。
- 统一标量打分替代插入顺序排序；跨层级竞争引入可调长度惩罚 λ。
- 交互模型切换为 rime 式分段确认：候选列表只显示活动段、确认即切段、剩余输入重新
  切分翻译；预编辑显示成为引擎的一等输出。
- 顺带根治第 1 节的全部结构 hack。
- 过渡期双引擎并存可回退，rime 引擎烘焙稳定后删除旧引擎，维护面回归单一。

### 非目标（明确不做）

- **不移植 rime 动态词频**（leveldb 用户库学习机制）：管理员明确不要。候选质量直接
  接现有 M2 UserDict（绝对值覆盖 + 调权 + 自造词 + 隐藏），语法组件用静态词频版。
- 不移植 punctuator / selector / opencc（iuv 已有）/ 配置 DSL / deployment /
  reverse_lookup：这些能力 iuv 已有等价物或不需要。
- Shift+左右箭头不让给 rime 的跨段选择——该键位已是 M2 调权（核心卖点）。
  键位细则见 §7。
- 不引入任何 FFI/C++ 依赖。

## 3. 总体策略：三步走 + 双引擎过渡

```
Step 0  任务书与契约修订（本文档 + 01-contract.md §4）
Step 1  先把现有引擎拆成「核心 + 适配层」，再定顶层接口签名，行为零变化
Step 2  用 Rust 改编 rime 引擎内核（新模块，REPL 可随时切换试用）
Step 3  配置开关二选一 + 会话切分段确认模型 → 烘焙 → 删除 classic
```

双引擎二选一是**过渡脚手架**（对拍 / A-B / 回滚用），不是长期特性。rime 引擎稳定
运行一个里程碑后删除 classic（git 留底）。移植成功后逐步裁剪用不上的功能。

预估总量 13–19 个智能体工作日。每步独立可交付、可回滚；UX 断裂集中在 Step 3 才发生。

## 4. Step 1：顶层接口缝（唯一签名面）

管理员定的原则：顶层接口本质就两份输入输出——

1. **用户输入字符串 → 候选列表**（附分段视图）。
2. **候选列表中键盘导航的高亮项 → 预编辑字符串**。例：输入 `jian`，候选是间/见/件…，
   导航到吉安时预编辑必须正确显示 `ji'an`。

据此定义唯一引擎 trait（示意，非最终代码）：`ImeEngine::translate(上下文, 待输入串)
-> Translation`，其中 Translation 含两个字段——`segmentation`（分段视图，含各段的
起止与标签）和 `candidates`（活动段候选列表，每条候选新增 score 浮点分）。
另有 `ImeEngine::preedit(上下文, 待输入串, 高亮候选) -> String` 返回高亮视角下的
预编辑显示串。上下文结构携带已确认前文（preceding_text）——classic 忽略它，
rime 引擎把它喂给组句打分，这是为 Step 3 预埋的关键钩子。

实施要点：

- **先拆后缝（管理员补充，2026-08-26）**：动手定接口之前，先把现有 Engine 与 Session
  里混杂的编排职责拆开——「引擎核心」= 纯粹的候选生成逻辑（吃待输入串与已确认前文，
  吐的口径就是上面的 Translation），剥离一切对会话状态机的反向依赖（如 rank_plans
  由 session 调用这类编排分裂）；「适配层」= 核心与 ImeEngine 接口之间的缝合。
  拆分的刀法直接按 rime 核心未来的形状下刀（分段视图、前文上下文、分数字段一律按
  目标口径设计），这样新核心落地时适配层零改动、只换核心实现。
- classic 引擎写一个适配器包进该接口：分段视图恒为整串一段；五个路由函数原样运转；
  Route 档位判定降级为适配器内部的标签计算。**全部既有测试保持绿 = 本步验收线**，
  会话层与交互完全不动。
- 会话层初期只消费 candidates 字段，segmentation 字段先放着不用——这就是 UX 变化
  后置到 Step 3 的伏笔。
- **快赢**：候选对象本来就存着撇号分隔的编码键（吉安 = ji'an），所以 classic 适配器
  在 Step 1 就能给出正确的 preedit()，`jian` 导航到吉安显示 `ji'an` 的诉求立即兑现，
  不必等新引擎。同时把现在散落在会话层的五条预编辑显示启发式收编进引擎接缝
  （现状是会话反向依赖引擎的音节合法性判断，层次颠倒）。

## 5. Step 2：Rust 改编 rime 引擎内核

新建独立模块（规划为 `crates/iuv-core/src/rime/`），从 librime 源码改编。
关键预期管理：这是「六成直译 + 四成重接」，不是逐行翻译。

### 直译清单（贴近 C++ 原构）

- navigator / segmentation：分段推进策略、段标签体系、回退分节器。
- composition / context 骨架：已确认段序列、活动段、组合文本维护。
- poet 组句：DP 与束搜索两种策略、左结合平局决胜、多句衰减公式。
  注意一处必须改写：C++ 版 Line 结构的前驱指针依赖 std::map 的指针稳定性，
  Rust 版改用 arena（索引池）表达，不能直译裸指针。
- uniquifier 等过滤器。

### 重接清单（查询层换血，天然是自己的代码）

- 音节图构建与查边：librime 建立在音节表/音节 ID trie 上，iuv-data 是去撇号字符串键
  的 mmap 词库。翻译器的骨架可移植，但查词必须重接 Dict 的精确/单字/首字母桶查询。
  这部分恰好等于自研方案本来要写的代码量，白捡的是 navigator/poet/编排细节。
- 语法组件：接 UnigramLm（静态词频 log 概率）+ M2 UserDict 合成权重；
  屏蔽表拦截从组句后置检查改为过滤阶段统一处理。
- 简拼：保留 iuv 现有构建期简拼键方案，作为简拼翻译器的政策（rime 原生走拼写代数，
  不照搬）。

### 明确不移植

动态词频用户库、punctuator、selector、opencc、配置 DSL、deployment、reverse_lookup。

### 性能与归属

- 性能基准点在「束搜索 × 字符串键查询」。若对拍超标，在加载期建音节 ID 索引层加速
  （IMEDIC02 数据格式不动）。
- 许可：librime 为 BSD-3-Clause。直译部分属于衍生作品——对应文件头部保留 librime
  版权声明，仓库加 NOTICE 说明；只参考行为规格自写的部分不受约束。混合形态合规且
  后续可随意修改裁剪。

### 过程保障

- REPL 增加 `--engine` 开关，全程可用真词库手测新引擎。
- 与 classic 引擎做语料对拍（见 §9），分歧逐项决策并记入本文档附录。

## 6. Step 3：切换、烘焙、删旧

- Config 新增引擎选项（Classic | Rime），过渡期设置页/REPL 可切。
- 会话状态机切换为分段确认模型：确认候选即切段；退格逐字退已确认段（汉字还原成拼音
  回到待输入区）；Esc/Enter 语义随新模型微调；启用 Step 1 预埋的 segmentation 字段。
- TSF 渲染小改：原文兜底候选改为显式类型标记，替换现有的「文本等于预编辑原文」
  字符串魔法协议。
- 烘焙一个里程碑无回归后删除 classic 引擎与过渡开关（git 留底）。

## 8. 替换后的手感变化（可预见清单）

确定会变：

| 场景 | 现在 | 替换后 |
|---|---|---|
| 整句地位 | 保底置顶 | 与词条按分数同场竞争；λ 校准前可能出现整句掉第二 |
| 到达低频层级 | 整串多级混排一页可达 | 取决于分段粒度：细粒度则单字仍在列；粗粒度需退格重切或段导航。**最大不确定项，Step 2 校准重点** |
| Backspace | 删拼音尾字符 | 逐字退已确认段，汉字还原成拼音 |
| 选中间词 | 悬空续接（内部机制） | 天然消失：确认即切段，行为等价但路径更明确 |
| 预编辑正确性 | 启发式拼凑 | 接口保证：导航吉安必显 ji'an |

不变：中英切换/四态/简繁/全角/标点尾巴、M2 调权·自造词·隐藏（读路径换成分数合成）、
TSF 契约、候选窗渲染、设置页。

## 10. 风险与对策

1. λ/cutoff 参数是按 rime essay 词库调的，白霜词库分布不同——Step 2 对拍期重调，
   预期几轮迭代。
2. navigator 分段粒度决定低频层级到达路径——Step 2 内先复刻 rime 原生粒度，
   手测不满意再调政策（分段策略本身可配）。
3. poet 束搜索性能——基准先行，超标则建音节 ID 索引层。
4. 双引擎期间每次改动要兼顾两条路径——过渡期尽量短，烘焙节奏明确。
5. 接口预埋不足导致 Step 3 签名返工——segmentation 与 preceding_text 已在 Step 1
   进契约。

## 13. 对拍分歧裁决记录（Step 2 实施中逐项落档）

| # | 分歧 | 裁决 | 依据 |
|---|---|---|---|
| 1 | librime 的 Segmentation/Context 段状态机与 ImeEngine「单活动段」接缝的关系 | **状态机不移植**，段生命周期归会话层（Step 3 分段确认模型） | navigator.cc 规格实证：打字期恒单段覆盖重译，多段仅在选字后出现；与 librime engine/translators 分层同构 |
| 2 | rime 简拼经拼写代数 vs iuv 构建期简拼键 | 简拼边携带**两族拼写**：该字母开头的全部音节（混拼展开 ni+hao→ni'hao）+ 字母串自身（命中压缩式简拼键 nhm/nhmsx）；查询时全字母路径用 concat 键、纯音节路径用 join' 键 | 白霜词库实测：简拼键为压缩式（exact("n'h'm")空、prefix("nhm")命中） |
| 3 | 中途简拼垃圾路径（nihao → 你会(ni'hui) 类）污染候选 | 顶点存在 Normal 出边时**只走 Normal/Completion**；简拼仅在无正常出边时启用（简拼=兜底的语言学事实） | classic 用户预期（微软对齐资产保序）；组合爆炸随之消失 |
| 4 | 词候选流跨类别排序 | 类 2（尾前缀补全，恒全跨度）置顶 → 类 0（纯全拼）→ 类 1（含简拼）沉底；类内终点降序。桶内同词多路径合并时类别取「含补全则 2，否则更纯者」 | classic 2b 整句置顶 + rime end-desc 铁律双重对齐 |
| 5 | 简拼边值长≠字节跨度的消费错位（你会@end3 却带 seg_len=2） | seg_len 改按**字节跨度映射贪心分段数**（librime end_pos 语义）；预测匹配恒 999 全消费 | 消除部分消费错位 panic 风险 |
